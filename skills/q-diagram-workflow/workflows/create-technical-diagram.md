# Create Technical Diagram

## 1. Capture Requirements

Record the audience, output medium, editability need, source data, and safety
constraints. For embedded diagrams, explicitly capture board names, connector
names, signal direction, voltage/current, power source, and what should not be
connected.

If the user points to existing PPTs or diagrams, export or inspect them first.
Use those as visual style references before creating a new figure.
If the user provides a corrected PPTX, copy or rename it to the formal source
path, compare it against the agent-generated source, and use export automation
only for producing PNG/PDF outputs. Treat the comparison as part of the task,
not optional cleanup.
For PPT component-library or reusable engineering-diagram work, use a
two-track strategy: Track A extracts editable grammar from accepted PPT-native
sources; Track B benchmarks AI-native diagram routes such as Mermaid, D2,
PlantUML, WaveDrom, WireViz, draw.io, or Kroki. Promote the AI-native route
only when rendered readability, editability/regenerability, PPT insertion
quality, and local/security fit beat or complement the PPT-native route.
When resuming or extending this benchmark, keep the latest Track A baseline in
the test matrix. If grid-first PPT-native layout has already been accepted for
simple regular block diagrams, include it as the PPT-native baseline instead
of testing only external renderers.
If recent user feedback rejected complex direct-PPT drawing, do not create a
new complex PPT-native sample as proof of progress. Return to the last
accepted/reviewed artifact and route matrix, then either migrate the accepted
simple/reference-aligned layout into a helper or test an ordinary page/layout
surface with the same grid contract.
For branded or template-constrained engineering PPT diagrams, identify the
applicable style source before drawing and treat its palette/symbol rules
as the color and symbol baseline.

For generated or reusable PPT work, decide the layout contract before choosing
individual coordinates. This applies to ordinary slide layouts as well as
diagrams: title/body zones, cards, screenshots, tables, callouts, flowcharts,
state machines, timing diagrams, and component-library preview pages should
derive from a safe area, grid boundary, named zones/cells, component slots,
text insets, ports, connector lanes, and label-clearance constants. Read
`../references/grid-first-layout-planning.md` when this is more than a
throwaway two- or three-shape sketch.

## 2. Choose Representation

Use this decision path:

- More than six point-to-point wires: use a high-level overview diagram plus a
  connection table.
- Exact connector pinouts or harness construction: use WireViz if available.
- User must edit the figure manually: create `.drawio` source.
- Training doc figure with labels and callouts: create `.pptx` or `.drawio`
  source, export PNG, and inspect the rendered PNG.
- Controller-to-driver handson connection diagram: use the style rules in
  `references/xiaoq-connection-diagram-style.md`; include exact endpoints only
  while straight, readable lines can be preserved.
- Flow/architecture/state/dependency: use D2, Graphviz, Mermaid, or Kroki.
- Simple slide block diagram with few branches and clear connectors: PPT-native
  shapes are acceptable.
- Complex slide block diagram with many branches, feedback paths, dense
  electronics relationships, or careful routing needs: plan with draw.io, D2,
  Graphviz, Mermaid, PlantUML, WireViz, or an explicit node/edge position plan
  before importing or restyling in PowerPoint.
- Slide deck output: create simple diagrams in PowerPoint, or import reviewed
  graphics from a better layout source.

For reusable PPT component-library diagrams, an imported PNG is acceptable only
as the slide display artifact. The route is promotable only when the editable
source is delivered beside it and can be manually changed and re-exported, such
as PPT shapes, `.drawio`, `.svg`, `.d2`, `.dot`, or another durable source
format. If a route only produces a bitmap/screenshot and cannot preserve an
editable source, reject that route for the component library.

For reusable PPT pages and component previews, choose one of these routes:

- PPT-native contract: use PowerPoint shapes generated by a helper that owns
  the page grid, component slots, node cells, ports, lanes, text insets, and
  label clearance.
- External editable source: use `.drawio`, `.svg`, `.d2`, `.dot`, Mermaid,
  PlantUML, WaveDrom, WireViz, or a similar source when the diagram semantics
  or routing are better handled outside PPT; import the reviewed PNG into PPT
  but keep the editable source beside it.
- Hybrid route: use an external source for layout/routing, then restyle or
  simplify in PPT only if the PPT output remains editable and the source
  contract stays documented.

Do not promote a route whose only durable artifact is a bitmap. Do not promote
a PPT-native route that needs independent per-shape nudges to look acceptable.

For style-critical electronics diagrams, prefer accepted editable
templates and a deliberate color palette over fully automatic layouts. Keep the
accepted structure grammar, but improve color semantics when older source
slides use nonstandard or low-contrast colors.

Do not assume that because an accepted picture was successfully reproduced as
PPT shapes, a new diagram from a text request will also lay out well. Direct
PPT generation is reliable only when the layout is already simple or already
solved by a reference image.

When a reference image is used for PPT-native reproduction, first identify its
grid: row centerlines, column x positions, repeated module sizes, group
boundaries, and arrow centerlines. Reproduce those coordinates deliberately.
Do not place boxes freely by visual guess. A well-aligned reference with
straight arrows can be reproduced as PPT shapes; an irregular layout should be
routed through a planning tool or a corrected source before PPT restyling.

For PPT-native block diagrams, create a quantized layout spec before drawing:
content safe area, grid origin, cell size, allowed box sizes, module cell
coordinates, side-center ports, and connector lanes. The grid can stay
invisible in the released slide, but the source/generator should still snap to
it. Use this path for diagrams that are simple enough for PPT but still need
professional alignment.
For ordinary PPT layouts, use the same method: define the slide safe area,
header/body/footer zones, columns/rows/gutters, component slots, text/image
slots, and inner component grids before drawing cards, rows, screenshots,
callouts, or summaries. A deck page laid out by scattered coordinates should
not be used as a reusable component-library baseline.
For reference-like block diagrams, do this as a planning step rather than a
post-placement cleanup: infer the whole diagram boundary and minimum grid unit
from the source image or requested figure size, define the full grid's rows and
columns, reserve node cells and line-lane cells separately, then render from
the grid boundary inward. Center the grid boundary inside the content safe
area; avoid shifting individual shapes to make the final picture look centered.
For any reusable grid-first diagram or page-layout helper, read
`../references/grid-first-layout-planning.md` and record the grid contract
before rendering the final artifact.

When a prior generated PPT missed obvious font size, border padding, wrapped
text, marker alignment, or connector-label placement, treat the next attempt as
a layout-contract repair. Fix the helper/contract and regenerate; do not only
move the offending shape in the final PPTX.

Avoid putting every pin, label, warning, and power note into one image.
Do not put production notes or internal design rationale in the released image;
keep those notes in project state, source comments, or nearby documentation.
For connection diagrams, place the most connected board near the center and
connect lines to module borders. Do not add a separate box for a connector such
as `VM/GND` if it is simply an input on the driver board.

## 3. Build Source

Keep the source close to the documentation:

- `docs/figures/*.drawio` for editable diagrams.
- `docs/figures/*.pptx` plus `*.png` for training figures that benefit from
  PowerPoint layout/editing and reliable visual review.
- `docs/figures/*.d2`, `*.dot`, `*.mmd`, or `*.wireviz.yaml` for diagram-as-code.
- `docs/figures/*.svg` only for simple generated or hand-authored overview
  graphics.

Name files after the target concept, not after a tool experiment.

## 4. Render

Render locally when a tool is available. If a renderer is missing, keep the
source and state that rendering was not validated.

Good local render targets:

- SVG for Markdown docs.
- PNG for visual inspection and slides.
- PNG for Markdown when SVG text rendering has caused overlap or font issues.
- PDF only for print or handoff packages.

## 5. Validate

Run the checks in `workflows/render-validate.md`. For training material, open
or inspect the rendered image before committing. If browser/headless export
fails, record that limitation and keep the source simple enough for manual
inspection.

## 6. Record

Update project state or task notes with the source format, output path,
validation result, and any missing renderer/tool installation.

If the user manually corrected the output, also record what changed and whether a
skill or reference was updated from the lesson.
