## Why use it?

Describe the concrete job and when the project is useful. Use a few supported
capabilities instead of generic superlatives. Omit this section if the opening
and example already explain the value.

## Get started

State real prerequisites and supported platforms. Give one recommended path.
If a maintained quickstart exists, link it instead of duplicating its commands.

Show the first useful action and its observable expected result. Keep important
installation side effects and limitations visible before the user executes it.

## Example or how it works

Choose a small real example, actual screenshot, compact table or diagram only
when it explains something better than prose. Do not add all four by default.

## Scope and limitations

List decision-relevant constraints, maturity and compatibility. Link detailed
reference material. Do not turn successful unit tests into broad quality claims.

## Documentation and updates

Point readers to existing guides by task: install, everyday use, configuration,
update, troubleshooting or release notes. Delete links with no maintained target.

## Contribute and get help

Name the actual maintainer/support route. Link existing contribution and security
policies; avoid publishing private contact details or suggesting secrets in issues.

## License

State the repository's actual license and link its file. Preserve third-party
notices and separate asset terms where applicable.
