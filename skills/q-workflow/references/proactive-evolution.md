# Proactive workflow evolution

Use when current work exposes a changed model/tool environment, stale workflow
assumptions, repeated friction, or a reusable lesson. This is an agent-executed
procedure during work, not a background service or a model-training mechanism.

- Trigger: a key milestone with a validated lesson or a confirmed task-relevant
  event during authorized work; ordinary task entry alone is not an upgrade trigger.
- Goal: improve the relevant workflow before the user has to repeat a correction.
- Strength / hardness: strong default to inspect meaningful signals; procedure
  for a candidate change. Authorization, privacy and validation gates still apply.
- Layer / tier: short entry check in q-workflow; this on-demand Project reference.
- Risk: read-only triage; scoped local maintenance only with applicable authority.
- Retirement: shrink the adapter if the host covers its detection, evidence,
  deduplication and recovery functions; retain the regression cases.

## 1. Notice a signal without turning work into an audit

Stability comes first. Passive notice is not an upgrade: ordinary work gains no
routine maintenance detour. Evaluate optional improvements only at the trigger
above and activate them at a safe checkpoint, after compatibility and regression
checks. If benefit or compatibility is uncertain, retain the validated working
route. A suspected opportunity can wait; required task validation cannot.
An observed safety, authorization or correctness failure still requires stopping
the affected action or an authorized safe repair, not waiting for a milestone.

At material-task entry, use facts already exposed by the current host and the
relevant skill files being loaded. Compare the last applicable review if it is
already routed through the private hub/work item. Do not enumerate tools, inspect
other sessions or search the web merely to fill this check. No change means
continue the user's task; do not announce an unchanged check.

Review the affected route when one of these is material:

- the host explicitly reports a different active model or changed tool contract;
- an exposed native capability can replace a costly workaround;
- the same workflow mistake recurs, a validator misses it, or an outdated rule
  conflicts with current instructions or prevents an otherwise supported action;
- a completed milestone provides a reusable successful method or counterexample.

Age, a newer-looking model name or a new release announcement is not proof that
a workflow is obsolete. Limit the first review to the route used by this task.
For urgency, limited budget or a stop/no-maintenance request, finish or pause the
requested task and defer optional maintenance. Do not open a portfolio-wide audit.

## 2. Establish what is actually known

Record an active model identity only when explicit current-session host metadata
or higher-priority session instructions identify it unambiguously. Distinguish
it from a configured default, selectable child models, a prior session, a user
label and a model's self-description. Otherwise use `unknown`; do not guess.
Do not rummage through unrelated logs or credentials to discover an identity.

Tool availability and permission are separate observations. An official API
feature may not exist in this host. Verify relevant current documentation when
needed, then use the actual tool schema and a safe task-shaped check. Unknown
model identity does not prevent useful capability-based review. Do not switch
models, buy capacity or change reasoning settings as part of this procedure.

## 3. Choose a bounded outcome

Name the concrete failure or opportunity, its owning file, the old invariant,
and one observable improvement criterion (correctness, fewer retries, less
context or simpler recovery). Choose one outcome:

| Outcome | Action |
| --- | --- |
| No change | Existing behavior remains useful; record why only if a material review occurred. |
| Local candidate | Patch the smallest owning rule/reference/test within authorized maintenance scope. |
| Defer | Preserve a concise proposal and revisit condition when record-writing is authorized. |
| Reject | Keep the useful existing behavior and the counterexample that ruled out this change. |

A task's write permission does not automatically authorize shared skill changes.
Use explicit local-maintenance permission or a clearly applicable standing user
preference; newer instructions can narrow or revoke it. Without that authority,
offer the observation without editing skills or creating unsolicited records.
Answer/diagnosis-only requests stay read-only. Do not turn a skill into a grant
of permission. An authorized correction need not wait for another reminder.

Prefer repair, simplification, reuse or retirement over adding rules. Follow
`workflow-evolution.md` for native replacement and `q-skill-creation` for source
ownership, change classification and proportional review. Safety, privacy,
publication and recovery invariants cannot be removed because a model is newer.
Dependency installs, shared-policy changes, migrations, destructive operations
and publishing need their own applicable authorization.

## 4. Validate, activate and make the result recoverable

Keep observation, candidate and accepted behavior distinct. Check the old
failure, one materially different case and a negative control where no upgrade
should occur. A passing file/schema check alone does not validate judgment.
Use required independent review for high-impact routing/policy changes; small
local repairs use targeted checks. Do not broaden testing after relevant checks
pass unless new evidence warrants it.

Activate only the validated scoped patch; preserve a previous revision or exact
diff for rollback. Synchronize declared source/runtime/bootstrap variants without
overwriting concurrent changes. If validation fails, leave live behavior intact,
record the failure where authorized and continue the original task when safe.
Local activation does not publish a release. Briefly report material changes to
the user; keep private task evidence outside public skills and README copy.

## 5. Avoid repeated checks and self-triggered upgrades

Use the existing private work item or hub decision history, not a second global
registry. Link the latest relevant review from its normal recovery entry point.
For a material review, retain only:

- observed model (or unknown), its evidence source, and relevant tool contract;
- owning skill/route, reviewed input revision and accepted output revision;
- signal/evidence, disposition, validation and rollback pointer;
- scope of authorization, next owner and concrete revisit condition.

Compare the accepted output revision on the next task; the maintenance patch
must not immediately trigger itself. Do not repeat no-change/rejected/deferred
reviews under the same conditions. New failure evidence, a changed relevant
capability, revised scope/authorization or a previously set review condition can
reopen them. An unchanged `unknown` identity is not a discovery trigger. Missing
history allows one bounded baseline review when authorized, not a full audit.

No recursive self-upgrade inside an upgrade. Capture newly found adjacent work
for a later authorized task. Do not create a timer, poll for model releases or
promise work after the session ends; use the product scheduler only if requested.

See [behavioral cases](proactive-evolution-cases.md) when changing this procedure.
