# PPT Intake Schema

Use the PPT intake schema when a deck request needs to move from a local HTML
form, another agent, a CLI runner, or a project handoff into the normal deck
creation workflow.

## Files

- `assets/ppt-intake.html`: static local intake page that exports request JSON.
- `schemas/q-ppt-intake.schema.json`: machine-readable schema for the exported
  request.
- `scripts/validate_intake_request.py`: standard-library contract checker for
  intake JSON and optional final slide-count validation.
- `examples/q-ppt-intake.example.json`: public-safe smoke-test request.
- `references/deck-creation.md`: generation, migration, visual grammar, and
  validation workflow that consumes the request.

## Default User Prompt

For ordinary `make a PPT` / `制作PPT` requests, the default user-facing action is
opening `assets/ppt-intake.html` and saying clearly: after exporting or copying
the JSON, tell the agent `开始制作` / `start making the PPT`; alternatively, paste
or type the request details directly in the current chat. This keeps the HTML
path discoverable without making it mandatory.

## Contract

The intake request captures user intent only. It is not the story brief, slide
map, layout IR, or final generator input. The receiving agent or runner must
still:

1. review the request and source materials;
2. produce a story brief;
3. produce a slide map/source freeze;
4. render or migrate the PPTX;
5. run structural readback, visual review, and default local PPTX open when
   available.

## Required Shape

Top-level fields:

- `schemaVersion`: must be `q-ppt-intake/v1`.
- `createdAt`: ISO timestamp generated by the intake tool or runner.
- `profile`: optional presenter identity and language preference.
- `deck`: title, audience, purpose, delivery format, language, density, optional
  exact slide count, and notes mode.
- `content`: source material pointers plus optional story-brief hints.
- `structure`: auto/manual section mode, optional target section count, and
  optional section names.
- `style`: selected base, visual motif, chart/table style, must-use items,
  must-avoid items, and optional reusable style id.
- `validation`: structural readback, sample-first, visual review, and final
  PPTX open choices.
- `output`: optional output path.
- `handoff`: target handoff mode and extra instruction text.
- `extensions`: optional object for namespaced private additions.

## Slide Count

Deck size is a contract. If `deck.targetSlideCount` is a positive integer, the
final deck must match that count unless the user explicitly approves a
downgrade. If `deck.targetSlideCount` is blank, convert `deck.density` into a
target range before slide-map generation:

- `short`: 6-8 slides
- `standard`: 10-14 slides
- `sharing`: 18-22 slides

Record the exact count or range in the slide map/source freeze and include the
actual generated slide count in validation evidence.

## Extensions

Keep the public root schema generic. Private variants may add fields under
`extensions.<namespace>` or ship a separate extension schema. Extension fields
should not be required for the public flow to work. Examples of extension-only
data include company classification labels, official template pack ids,
restricted asset paths, brand-specific navigation families, and private runner
settings.

## Handoff Checklist

- Intake JSON path is recorded.
- `scripts/validate_intake_request.py <request.json>` passes before generation.
- Story brief and slide map/source freeze were created from the intake request.
- Generated or migrated PPTX exists.
- `scripts/validate_intake_request.py <request.json> --actual-slide-count N`
  passes after generation when the slide count is known.
- Structural readback records slide count and titles.
- Visual review ran or the skip reason is explicit.
- Final PPTX was opened locally by default, or the environment limitation is
  recorded.
